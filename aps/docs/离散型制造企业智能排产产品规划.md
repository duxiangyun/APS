## 一、产品概述

### 1.1 产品定位

本产品是一款面向**多品种、小批量、定制化程度高**的离散制造企业的**智能高级计划与排程系统（APS）**。它以运筹优化算法为核心引擎，在**有限产能、物料齐套、工艺顺序、换型时间**等多重现实约束下，自动生成**精准到工序、设备、班次级**的可执行生产计划，并支持**实时监控、异常预警与动态重排**，帮助企业实现**计划与执行一体化闭环管理**。

### 1.2 核心理念

> **数据驱动决策，算法创造价值，闭环持续优化。**

产品不只是一个"计算工具"，而是一个**能实时应对变化、持续自我进化**的智能生产决策中枢。

### 1.3 目标客户画像

| 维度 | 特征描述 |
|:---|:---|
| **目标行业** | 汽车零部件、电子制造、装备制造、医疗器械、精密加工、印刷包装 |
| **企业规模** | 年产值1亿元以上，设备/产线数量50台（条）以上，计划员≥3人 |
| **核心痛点** | 订单变更频繁、工序复杂、换型时间长、设备昂贵、准时交付压力大 |
| **现有系统** | 已部署ERP（如SAP、用友、鼎捷），部分已上MES |

| **约束建模** | 固定逻辑 | 可配置 | 可配置 + 替代工艺/物料 |

| **行业适配** | 通用 | 通用 | 离散制造深度适配 |

## 二、核心应用场景

### 2.1 场景总览

| 场景 | 典型痛点 | 系统解决方案 |
|:---|:---|:---|
| **1. 接单排产** | 销售接单后无法快速判断能否按时交付 | 自动展开 BOM + 工艺路线 + 产能校核，秒级给出交期承诺（CTP） |
| **2. 多订单批量排产** | 数十/上百订单同时排产，人工排不过来 | 数学规划求解器一次性优化全部订单的工序排程 |
| **3. 插单/改单应对** | 紧急插单打乱原计划，人工重排耗时 | 增量排产，锁定已开工工序，仅重排未开工部分 |
| **4. 产能瓶颈识别** | 不清楚哪台设备/哪个时段是瓶颈 | 甘特图 + 资源负荷率热力图，直观定位瓶颈 |
| **5. 物料齐套分析** | 排了计划但物料不齐，无法执行 | BOM 展开后与库存/采购到货时间比对，提前预警缺料 |
| **6. 外协决策** | 自制产能不足时何时外协、外协给谁 | 对比自制成本 vs 外协价格，在产能约束下自动分配 |
| **7. 在制品管理** | 不清楚车间在制品状态和进度 | 录入完工进度，滚动排产时自动扣除已完成工序 |
| **8. 滚动排产** | 计划赶不上变化，需要周期性更新 | 按日/周滚动，冻结近期已下达计划，重排远期计划 |

### 2.2 典型业务模式

#### 按单生产（MTO）的订单排产

| 维度 | 说明 |
|:---|:---|
| **业务背景** | 客户下单后才开始排产，订单带有明确交期和延期罚金条款 |
| **核心痛点** | 产能不足时哪些订单优先交付、哪些延期损失最小难以人工判断 |
| **系统价值** | 以"销售收入 - 延期罚金"最大化为目标，自动给出订单优先级与交付方案 |
| **适用行业** | 机械装备、电子代工、模具制造、定制化零部件加工 |

#### 按库存生产（MTS）的产能均衡

| 维度 | 说明 |
|:---|:---|
| **业务背景** | 根据预测或安全库存组织生产，需在多产品间分配有限产能 |
| **核心痛点** | 旺季产能不足、淡季产能闲置，库存积压或缺货风险并存 |
| **系统价值** | 综合库存成本、产能利用率、缺货惩罚，给出各产品的均衡生产量 |
| **适用行业** | 日化、食品、建材、标准化零部件 |

#### 瓶颈产能下的加班/外协决策

| 维度 | 说明 |
|:---|:---|
| **业务背景** | 关键设备产能成为瓶颈，需决策是否加班、是否外协 |
| **核心痛点** | 加班成本 vs 延期罚金 vs 外协成本的三方权衡复杂 |
| **系统价值** | 模型内置加班、外协决策变量，自动给出成本最优的组合方案 |
| **适用行业** | 精密加工、半导体、印刷、注塑 |

#### 物料替代与采购联动

| 维度 | 说明 |
|:---|:---|
| **业务背景** | 原材料存在替代关系，采购到货时间影响生产排程 |
| **核心痛点** | 替代比例、采购提前期、库存水平多重耦合，人工难以统筹 |
| **系统价值** | 联动考虑替代比例约束、采购限制与库存平衡，输出采购与替代建议 |
| **适用行业** | 化工配方、食品原料、金属材料替代 |

### 3.2 流程步骤详解

| 步骤 | 操作内容 | 关键产出 | 参与角色 |
|:---|:---|:---|:---|
| **1. 订单录入** | 通过 API 从 ERP 拉取或手工录入客户订单（产品/数量/交期），设定优先级 | 订单池（含交期、数量、优先级） | 计划员 |
| **2. BOM 展开** | 根据产品代码递归展开 BOM 树，计算各层物料净需求 | 物料需求清单 | 系统（自动） |
| **3. 工艺匹配** | 匹配工艺路线，支持替代工艺选择 | 工序序列 + 设备/工装需求 | 系统（自动） |
| **4. 产能校核** | 统计各设备各时段负荷率，初步判断产能是否充足 | 产能负荷报告 | 系统（自动） |
| **5. 物料齐套** | 物料需求与库存/采购到货时间比对，标记缺料风险 | 齐套分析报告 | 计划员、采购员 |
| **6. 排产求解** | 运筹优化算法在多重约束下，生成工序级最优排程 | 最优排产方案（甘特图） | 系统（算法自动执行） |
| **7. 计划下达** | 确认后的计划下发至 MES / 车间电子看板 / 派工单 | 车间可执行工单 | 计划员、车间主任 |
| **8. 执行跟踪** | 车间完工反馈实时回传，比对"计划 vs 实绩" | 实时进度看板、偏差报告 | 计划员、车间主任 |
| **9. 滚动排产** | 发生异常或新订单时，冻结近期已下达计划，重排远期 | 更新后的可执行计划 | 计划员、系统（算法） |

> **闭环价值**：步骤 8 的实绩数据反馈直接修正步骤 6 的算法输入（如在制品状态、标准工时），形成"**排程 → 执行 → 反馈 → 优化排程**"的持续改进飞轮。

## 四、产品功能架构

系统采用五层分层架构，自下而上为**数据层 → 算法层 → 应用层 → 用户层**，并辅以**集成层**贯穿全局。

```
┌─────────────────────────────────────────────────────────────────────┐
│                          用户层                                      │
│   生产计划员  |  车间调度员  |  销售人员  |  管理层                   │
├─────────────────────────────────────────────────────────────────────┤
│                          应用层 (Web)                                │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ 主数据    │ │ 排产控制  │ │ 结果展示  │ │ 分析看板  │ │ 系统管理  │ │
│  │ 管理      │ │ 中心      │ │ 甘特图    │ │ 负荷分析  │ │ 配置/权限 │ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘ │
├─────────────────────────────────────────────────────────────────────┤
│                          算法层                                      │
```

| 层级 | 职责 | 技术实现 |
|:---|:---|:---|
| **用户层** | 面向不同角色提供差异化界面 | 浏览器访问，基于角色权限控制 |
| **应用层** | 业务功能承载，连接用户与算法 | Flask Web 应用，Jinja2 模板 |
| **算法层** | 数据预处理 → 模型构建 → 求解 → 结果解析 | Python + Gurobi 混合整数规划 |
| **数据层** | 三层数据架构：原始 → 核心标准化 → 算法视图 | SQLite，stg_/core_/alg_ 视图 |
| **集成层** | 与外部系统数据交换 | Excel 导入导出 + REST API |

**差异说明**：
1. **两侧已打通**：统一壳（`web`）为角色唯一真源。右上角切换角色 → ① Agent 侧 `/chat/stream` 与 `/skills?role=` 带新角色并开启新会话；② APS iframe `src="/aps/dashboard?role=<role>"` 带新参数重新加载，APS 侧 `static/js/role_control.js` 按 `ROLE_MENUS` 控制侧边栏可见性（iframe 内跳转时经 sessionStorage 记住角色）。
2. Agent 的 `role` 由前端状态模拟（`web/src/types.ts` 注释"前端状态模拟，不做登录"），APS 侧同样无登录，统一壳可作为角色的唯一真源（`?role=` 深链仅作演示覆盖）。
3. sales 角色在 Agent 侧的工具集按此限定为订单/排产类只读工具（`get_orders`、`get_schedule`）；`get_order_delivery`、CTP 类工具尚未实现，待新增后再扩容。
4. 9 个角色已全部在 Agent 侧与 APS 侧对齐（原缺的 **sales** 与 **masterdata** 本次补齐）。
5. **仍缺**：后端用户表/会话与按钮级写操作鉴权——当前角色控制为前端菜单可见性 + Agent 工具白名单，直接请求 APS 写接口仍不会被拒绝。

#### 6.4.5 实现建议

1. **APS 侧（菜单级可见性控制）**
   - `constants.py` 的 `SIDEBAR_MENU` 为每个一级菜单补充 `roles: [...]` 字段（或菜单 key 即 `data-menu` 属性，以 6.4.2 矩阵为默认授权表）；
   - `templates/base.html` 渲染时在菜单节点输出 `data-menu="{{ menu.key }}"`，前端 JS 读取当前角色后按矩阵隐藏/显示（当前角色可由统一壳通过 URL 参数或 postMessage 注入 `window.APS_ROLE`）；
   - 服务端兜底：页面路由按角色返回 403（菜单隐藏仅为 UX，不能替代鉴权）；写接口 `/api/edit/*`、`/api/solve/start`、`/api/whatif/*` 必须做服务端角色校验；
   - 前提：需先落地用户表/会话（规划 46/47），建议最小实现 `user(id, username, role, password_hash)` 单表 + Cookie 会话，无需复杂 RBAC 表。
2. **统一壳侧（角色同步）**
   - 统一壳加载 APS iframe 时携带角色：`iframe src = /aps/dashboard?role=planner`；
   - 壳内切换角色时通过 `postMessage({type: 'role_change', role: 'sales'})` 通知 APS，APS 监听后更新 `window.APS_ROLE` 并重刷菜单可见性；
   - 同一角色信息同步推给 Agent（Agent 已支持请求体 `role` 字段），保证三端（壳/APS/Agent）角色一致。
3. **Agent 侧**
   - 已有 7 角色控制，需新增 **sales** 和 **masterdata** 两个角色：
     - sales：工具白名单限定订单/交付/CTP 类只读工具
     - masterdata：工具白名单限定 BOM/工艺/物料查询类工具
     - 前端 `RoleKey`/`ROLE_OPTIONS` 同步加两项（`ROLE_KEYS` 与角色解析正则同步加入两个角色）；
   - 审计日志 `audit.py` 已按 role 记录，无需结构调整。
